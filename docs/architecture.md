# 식당 추천 시스템 아키텍처 설계 가이드

우리는 유지보수성이 높은 시스템을 설걔하기 위해 계층형 아키텍처와 Specification 패턴, 싱글톤 패턴을 채택했습니다.

## 1. 아키텍처 설계 (Layered Architecture)
코드의 역할을 명확히 분리하여 유연한 시스템을 구축하기 위해 3계층 구조를 적용합니다.

### Presentation Layer (UI / Controller 계층)
* **역할:** 사용자와의 직접적인 상호작용 및 입출력 담당.
* **주요 흐름:**
    - 사용자가 메인 화면에 접속하여 조건 입력.
    - 추천 버튼 클릭 이벤트 처리. 
    - 추천 결과 화면 출력 또는 조건 미충족 시 안내 문구 표시.

### Business Logic Layer (Service 계층)
* **역할:** 시스템의 핵심 비즈니스 로직(필터링 알고리즘) 수행.
* **주요 흐름:**
    - 입력받은 조건에 따라 식당 데이터를 필터링하는 로직 실행.

### Data Access Layer (Repository 계층)
* **역할:** 외부 데이터 원본(JSON 등)에 접근하여 데이터를 로드 및 관리.
* **주요 흐름:**
    - `restaurants.json` 파일을 불러와 시스템이 사용할 수 있는 객체 형태로 변환.

## 2. 디자인 패턴

### 패턴 A: 명세 패턴 (Specification Pattern)
* **적용 위치:** Business Logic Layer (식당 검색 및 필터링 로직)
* **도입 이유:** 사용자가 '음식 종류', '가격대', '식사 목적' 등 다양한 검색 조건을 단독 또는 조합하여 선택할 수 있으므로, 복잡한 조건문과 경우의 수 증가를 방지하기 위해 각 검색 조건을 독립적인 명세(Specification)로 분리합니다.
* **기대 효과:**
    - **확장성 향상:** 새로운 검색 조건(예: 평점, 영업 여부, 주차 가능 여부 등) 추가 시 기존 로직 수정 없이 새로운 명세만 추가 가능하여 개방-폐쇄 원칙(OCP)을 준수.
    - **유지보수성 향상:** 각 검색 조건이 독립적으로 관리되어 코드의 응집도가 높아지고 조건 변경 시 영향 범위가 최소화됨.
    - **조건 조합의 유연성:** 사용자가 선택한 검색 조건을 동적으로 조합하여 다양한 검색 시나리오를 효율적으로 처리 가능.

### 패턴 B: 싱글톤 패턴 (Singleton Pattern)
* **적용 위치:** Data Access Layer (데이터 로드 객체)
* **도입 이유:** 추천 버튼을 누를 때마다 파일에서 데이터를 새로 읽어오는 비효율을 방지합니다.
* **기대 효과:**
    - **성능 최적화:** 애플리케이션 초기 실행 시 데이터를 메모리에 한 번만 로드하여 자원 낭비 최소화.
    - **객체 공유:** 메모리에 로드된 객체를 재사용함으로써 시스템 속도 향상.
